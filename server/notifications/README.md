# Personal status notifications

This module evaluates existing quota snapshots and fixed-target server samples without calling inference endpoints. Balances strictly below CNY 5 / USD 1 and subscription remaining fractions below 0.1 generate events. Confirmed recoveries require two fresh observations; reset alerts require verified cycle evidence. Unknown, stale and failed collection never mean zero quota. Sampling-unreachable is distinct from a powered-off server. Repeated observations and process restarts do not duplicate events.

The host authenticates every request and initially restricts these personal sources to its configured owner. The inbox, category preferences, read state and private device registry use SQLite outside the web root, mode 0600. Tokens must not appear in responses, logs, model inputs or public configuration. `http.handle` integrates the fixed `/api/hub/notifications` prefix after the host's existing account gate. DELETE device registration must also pass the same gate. Use no-store responses.

Android uses a user-started visible foreground monitor, ordinary system notification permission, same-origin HTTPS minute polling and encrypted local session storage. It does not require a manufacturer SDK or enterprise developer account. It does not silently request battery exemptions, restart after a user stop, or guarantee service survival under force-stop/OEM power management. Its service uses the declared specialUse foreground category; public app-store distribution requires a separate eligibility review. The first successful snapshot is a baseline; only fresh, unread, new eligible events notify. Logout invalidates outstanding request generations and stops monitoring.

iOS uses explicit notification permission and real APNs registration. Its signing profile must include the production push entitlement for TestFlight, and the private server must have an actual APNs-authorized key. An App Store Connect key is not automatically an APNs key. Until configured, expose `not_configured`; receiving a token or HTTP 200 from Apple does not prove a visible device notification.

The optional APNs outbox has a five-minute TTL, generic lock-screen payload, settings filtering, live-device revalidation and bounded retry of explicit transient rejections. A lost response is unknown rather than blindly replayed. An old invalid-token response cannot disable a newly rotated token. The client reads private details only after authentication.

Run `python3 -m unittest discover -s server/notifications` from the repository root. All tests use temporary stores and synthetic observations; none sends notifications. Deployment requires private cache and monitor paths; private credentials are never included here. Back up the notification SQLite database with its online backup API, not a raw copy of a live WAL database.
